# Zyven Architecture

Zyven is a framework that allows autonomous AI agents to compile and verify their own Model Context Protocol (MCP) tools on demand from open-source libraries, keeping only skills that pass a multi-gate sandbox.

---

## 1. System Overview & Core Philosophy

Language models excel at qualitative reasoning, planning, and language generation, but are notoriously prone to errors when computing exact deterministic logic:
- Check digits and checksums (Luhn, IBAN, ISBN, Modulo 97)
- Calendar conversions (Gregorian ↔ Hijri, Bikram Sambat, Hebrew)
- Specialized formatting and telephony validation (E.164, region extraction)
- Exact symbolic mathematics (differentiation, polynomial factoring, definite integrals)

Rather than having human developers hand-craft MCP servers for every domain or letting models hallucinate arithmetic, Zyven automatically wraps open-source libraries into hardened MCP servers.

**Guiding principle:** *The model proposes; the harness decides.*
- No code generated by an AI model is trusted until verified.
- No repository code is ever executed directly on the host machine.
- Static analysis is strictly deterministic and never executes untrusted repository source code.

## 3. End-to-End Execution Flow

When a user submits a task to the self-extending agent:

```
[ User Task ]
      │
      ▼
[ 1. Gap Check ] ──(Tools sufficient?)──► [ Direct Execution with Current Tools ]
      │ (Missing capability needed)
      ▼
[ 2. Skill Library Check ] ──(Already verified in library?)──► [ Hot-load & Reuse ]
      │ (Not in library)
      ▼
[ 3. Catalog Match ] ──► Matches against pinned repo catalog (`catalog/repos.json`)
      │
      ▼
[ 4. Human Approval Gate ] ──(Rejected)──► [ Decline / Unverified Model Attempt ]
      │ (Approved by user)
      ▼
[ 5. Capability Compilation ]
      │
      ├─► Scout / Architect: Design candidate MCP capability (`CapabilitySpec`)
      ├─► Interface Lint: Enforce single-format inputs, rich return fields
      ├─► Compiler: Propose tool adapter bodies (`AdapterCode`)
      ├─► Tester: Independently generate differential test cases (`DiffTests`)
      ├─► Assembly: Assemble `server.py` with scoped imports per tool
      │
      ▼
[ 6. Multi-Gate Docker Sandbox ]
      │
      ├─► Gate 1: Static Policy Check (no os/sys/subprocess/network/file write)
      ├─► Gate 2: Clean Import Test
      ├─► Gate 3: Upstream Repository Test Suite
      ├─► Gate 4: Input Robustness (whitespace, edge cases, type variants)
      ├─► Gate 5: MCP Smoke Test (protocol handshake, list_tools, call_tool)
      ├─► Gate 6: Differential Equivalence (Adapter vs Direct Library Call)
      │
      ├──(Failures detected)──► [ Bounded AI Repair Loop (max 2 rounds) ]
      │                                    │
      │◄───────────────────────────────────┘
      │
      ├──(Passed all gates)──► [ Verified Skill Package: server.py, provenance.json, etc. ]
      │                             │
      │                             ▼
      │                      [ Hot-load into ToolBox & Cache into SkillLibrary ]
      │                             │
      ▼                             ▼
[ 7. Agent Resumes Task ] ──► Produces verified final answer with proven tool calls
```

## 4. Subsystem Details

### 4.1 Static Analysis (`zyven/analysis/`)
- **Deterministic AST Parser:** Inspects repository Python source files using `ast.parse`. Extracts public functions, classes, methods, docstrings, type annotations, and call graphs.
- **Side-Effect Detection:** Flags functions that interact with the environment, filesystem (`open`), code evaluation (`eval`, `exec`), or randomness.
- **Reference Resolver (`RefResolver`):** Verifies that symbol identifiers proposed by AI models (e.g. `stdnum.iban.validate`) resolve strictly to valid symbols extracted from the static analysis, rejecting hallucinations before code assembly.

### 4.2 AI Roles (`zyven/ai/roles.py`)
Zyven divides capability creation into 5 focused AI roles, each with strict boundaries:
1. **Scout:** Discovers capabilities worth compiling from the AST digest.
2. **Architect:** Shapes the MCP tool boundary, parameter types, and return fields.
3. **Compiler:** Implements tool adapter bodies that import and invoke library symbols.
4. **Tester:** Independently generates test cases calling the library directly. It **never** sees the adapter code proposed by the Compiler, preserving adversarial independence.
5. **Repair:** Receives specific gate failure outputs and refactors only the failing tool implementations under strict token budgets.

### 4.3 Compiler & Static Policy (`zyven/compiler/`)
- **Import Scoping:** Generates local imports within each tool function body to prevent namespace pollution or accidental module shadowing across tools.
- **AST Security Policy:** Disallows non-pure standard library packages (`os`, `sys`, `subprocess`, `socket`, `shutil`, `urllib`, `requests`) and dangerous built-ins (`__import__`, `eval`, `exec`, `open`).

### 4.4 Docker Sandbox Runner (`zyven/sandbox/`)
- Runs in an isolated Linux container (`zyven-sandbox:py312`).
- **Flags:** `--network none`, `--rm`, `--read-only`, non-root user execution, memory limits (`1GB`), and CPU limits (`1 CPU`).
- Untrusted repository code and generated adapter code run **exclusively** inside this sandbox.

### 4.5 Agent Loop & Memory (`zyven/agent/`, `zyven/memory/`)
- **ToolBox:** Spawns local MCP server subprocesses over stdio, discovering tools via standard JSON-RPC protocol.
- **SkillLibrary:** Persists verified skills with immutable provenance (repository URL, commit hash) and tracks call health (success/failure rates across tasks).

## 5. Trust Boundaries & Threat Model

| Boundary | Inbound / Outbound | Security Mechanism |
|---|---|---|
| **External Repository Source** | Inbound from GitHub | Cloned only at fixed immutable commits (`catalog/repos.json`). AST analyzed offline; never executed on the host. |
| **Model Generation** | Inbound from LLM | Parsed with strict Pydantic schemas. Symbols verified by `RefResolver`. Code checked by AST policy before sandbox execution. |
| **Sandbox Execution** | Adapter & Tests → Container | Docker container with `--network none`, read-only roots, non-root user, CPU/memory limits, dropped capabilities. |
| **Human Approval** | Agent → Human Reviewer | The agent cannot compile or load outside code without explicit user approval via UI/API (`/api/cards/{id}/decision`). |
| **Model Verification Overclaim** | Failed Compile → Agent | If verification fails, the agent is explicitly instructed that the capability is unverified, tools are withheld, and cards enter `UNVERIFIED` state. |
