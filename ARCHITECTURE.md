# Zyven Architecture

Zyven is a framework that allows autonomous AI agents to compile and verify their own Model Context Protocol (MCP) tools on demand from open-source libraries, keeping only skills that pass a multi-gate sandbox.

---

## 1. System Overview & Core Philosophy

Language models excel at qualitative reasoning, planning, and language generation, but are notoriously prone to errors when computing exact deterministic logic:
- Check digits and checksums (Luhn, IBAN, ISBN, Modulo 97)
- Calendar conversions (Gregorian ↔ Hijri, Bikram Sambat, Hebrew)
- Specialized formatting and telephony validation (E.164, region extraction)
- Exact symbolic mathematics (differentiation, polynomial factoring, definite integrals)

Rather than having human developers hand-craft MCP servers for every domain or letting models hallucinate arithmetic, Zyven automatically wraps open-source libraries into hardened MCP servers.

**Guiding principle:** *The model proposes; the harness decides.*
- No code generated by an AI model is trusted until verified.
- No repository code is ever executed directly on the host machine.
- Static analysis is strictly deterministic and never executes untrusted repository source code.

## 3. End-to-End Execution Flow

When a user submits a task to the self-extending agent:

```
[ User Task ]
      │
      ▼
[ 1. Gap Check ] ──(Tools sufficient?)──► [ Direct Execution with Current Tools ]
      │ (Missing capability needed)
      ▼
[ 2. Skill Library Check ] ──(Already verified in library?)──► [ Hot-load & Reuse ]
      │ (Not in library)
      ▼
[ 3. Catalog Match ] ──► Matches against pinned repo catalog (`catalog/repos.json`)
      │
      ▼
[ 4. Human Approval Gate ] ──(Rejected)──► [ Decline / Unverified Model Attempt ]
      │ (Approved by user)
      ▼
[ 5. Capability Compilation ]
      │
      ├─► Scout / Architect: Design candidate MCP capability (`CapabilitySpec`)
      ├─► Interface Lint: Enforce single-format inputs, rich return fields
      ├─► Compiler: Propose tool adapter bodies (`AdapterCode`)
      ├─► Tester: Independently generate differential test cases (`DiffTests`)
      ├─► Assembly: Assemble `server.py` with scoped imports per tool
      │
      ▼
[ 6. Multi-Gate Docker Sandbox ]
      │
      ├─► Gate 1: Static Policy Check (no os/sys/subprocess/network/file write)
      ├─► Gate 2: Clean Import Test
      ├─► Gate 3: Upstream Repository Test Suite
      ├─► Gate 4: Input Robustness (equivalent inputs must give the same result)
      ├─► Gate 5: MCP Smoke Test (protocol handshake, list_tools, call_tool)
      ├─► Gate 6: Differential Equivalence (Adapter vs Direct Library Call)
      │
      ├──(Failures detected)──► [ Bounded AI Repair Loop (max 2 rounds) ]
      │                                    │
      │◄───────────────────────────────────┘
      │
      ├──(Passed all gates)──► [ Verified Skill Package: server.py, provenance.json, etc. ]
      │                             │
      │                             ▼
      │                      [ Hot-load into ToolBox & Cache into SkillLibrary ]
      │                             │
      ▼                             ▼
[ 7. Agent Resumes Task ] ──► Produces verified final answer with proven tool calls
```

## 4. Subsystem Details

### 4.1 Static Analysis (`zyven/analysis/`)
- **Deterministic AST Parser:** Inspects repository Python source files using `ast.parse`. Extracts public functions, classes, methods, docstrings, type annotations, and call graphs.
- **Side-Effect Detection:** Flags functions that interact with the environment, filesystem (`open`), code evaluation (`eval`, `exec`), or randomness.
- **Reference Resolver (`RefResolver`):** Verifies that symbol identifiers proposed by AI models (e.g. `stdnum.iban.validate`) resolve strictly to valid symbols extracted from the static analysis, rejecting hallucinations before code assembly.

### 4.2 AI Roles (`zyven/ai/roles.py`)
Zyven divides capability creation into 5 focused AI roles, each with strict boundaries:
1. **Scout:** Discovers capabilities worth compiling from the AST digest.
2. **Architect:** Shapes the MCP tool boundary, parameter types, and return fields.
3. **Compiler:** Implements tool adapter bodies that import and invoke library symbols.
4. **Tester:** Independently generates test cases calling the library directly. It **never** sees the adapter code proposed by the Compiler, preserving adversarial independence.
5. **Repair:** Receives specific gate failure outputs and refactors only the failing tool implementations under strict token budgets.

### 4.2b The Tester's reference programs
Each differential case carries a `reference_expr`: a short Python **program** (setup statements, then a last line that is one
expression) that calls the library directly. `compiler/verify.py::_differential_gate` parses it with `ast`, requires the last
line to be an expression, and passes every line through the same `check_adapter` policy as adapter code; rejected cases are
reported with the reason. Example arguments are converted to the declared parameter types first (`typed_args`: list and object
parameters arrive as real lists and objects, not JSON text). The program is evaluated inside the sandbox by
`sandbox/diff_check.py::evaluate` and its value is compared with the tool's output.

### 4.3 Compiler & Static Policy (`zyven/compiler/`)
- **Import Scoping:** Generates local imports within each tool function body to prevent namespace pollution or accidental module shadowing across tools.
- **AST Security Policy (an allowlist):** generated code may import only the source package, `mcp`, and a short list of pure stdlib modules (`datetime`, `re`, `math`, `decimal`, `json`, `functools`, `calendar`, …). Everything else, `os`, `sys`, `subprocess` and `socket` included, is rejected. Calls to `open`, `exec`, `eval`, `compile`, `__import__`, `globals`, `locals`, `vars`, `input`, `setattr` and `delattr`, introspection attributes such as `__globals__` and `__subclasses__`, and `global`/`nonlocal` are rejected too. The check runs before any execution.

### 4.4 Docker Sandbox Runner (`zyven/sandbox/`)
- Runs in an isolated Linux container (`zyven-sandbox:py312`).
- **Flags:** `--network none`, `--rm`, `--read-only` with a 256 MB `/tmp`, user `1000:1000`, `--cap-drop ALL`, `no-new-privileges`, and limits of 1 GB memory, 2 CPUs and 256 processes (defaults in `zyven/sandbox/runner.py`).
- Untrusted repository code and generated adapter code run **exclusively** inside this sandbox: during the verification gates, and again at runtime, when the agent uses a verified skill (see 4.5). One function, `docker_args()`, defines the flags for both.

### 4.5 Agent Loop & Memory (`zyven/agent/`, `zyven/memory/`)
- **ToolBox:** Launches each skill's MCP server over stdio **inside the sandbox container** (`docker run -i`, same flags as verification, skill and pinned source mounted read-only) and discovers its tools over MCP. Starting the container costs about 1–2 s, once per skill per task. Running a skill on the host is a development-only opt-in (`ZYVEN_SKILL_RUNTIME=host`), logged on every launch.
- **Gap check:** `gap_check` sees only `verified_tools(...)`: the agent's command tools (`run_command`, `run_command_with_network`)
  are hidden from it, because code the agent writes itself is not a verified implementation. Whether the model then reports a
  gap is still its own judgement (see `LIMITATIONS.md`).
- **Connections at start-up:** `connections/runtime.py::load_enabled` connects each enabled connection in turn with a 30 s limit;
  one that does not answer is skipped and reported.
- **SkillLibrary:** Persists verified skills with immutable provenance (repository URL, commit hash) and tracks call health (success/failure rates across tasks).

### 4.6 Control Center & Runtime Adapters (`zyven/orchestrator/`)
The Control center queues, schedules (once or repeating), cancels and observes **runs**, each on a *runtime*. The built-in
Zyven agent runs as a board card. Every other runtime is an adapter (`adapters.py`) implementing `run(ctx)` and
`cancel()`; the Control center keeps the queue, repeats, repo checkout, per-run folder, before/after file diff and status.

- `DockerAdapter`: one command in a container. `GitHubAdapter` (`github_adapter.py`): validated JSON task, the exact `gh`
  command shown on an approval card, private repositories by default.
- `CLIAgentAdapter` (`cli_agent.py`) is the base for **Codex, OpenCode, the Qoder CLI, Claude Code and Antigravity**. It gives each the
  same handling: prompt on stdin (never a command line); an absolute task folder with `PWD` pinned to it (OpenCode trusts
  `$PWD` over the real working directory); stderr kept apart from the event stream; an idle timeout (paused while an
  approval is pending); process-tree kill on cancel; a refusal to run a checked-out repository that ships its own agent
  settings; and a non-blocking installed / signed-in check (cached for a minute, refreshed in the background).
- Each program's own containment is used and checked: Codex runs in `workspace-write` with the system temp folders and
  network closed, **without loading the user's config** (`--ignore-user-config`, computer-use, browser and apps features
  disabled: a user's own plugins and MCP tools act outside Codex's sandbox); OpenCode gets a project `opencode.json`
  denying shell, web and anything outside the folder; Claude Code gets a tool allowlist without a shell, `acceptEdits`,
  and the repository's own settings ignored.
- **Qoder CLI** (`qoder_adapter.py`): `qodercli -p -o stream-json`, built-in tools limited to Read, Write, Edit, Glob and Grep
  (the variadic `--tools` option is last), `accept_edits`, and Zyven's tools through a `.zyven-mcp.json` in the task folder
  (the token stays out of the command line). Its event stream has Claude Code's shape, so the parser is shared. It reports zero
  token usage, so Zyven does not claim counts. The model is the user's choice; which weights and host answer is not verified.
- **Approvals** (`ctx.approve`): a run asks before an outward action and blocks until the user decides; denial, a one-hour
  timeout, a cancel and a restart all mean no. **Full PC access** is a per-task opt-in (an environment switch plus a
  confirmation, not repeatable, badged) that selects each program's own no-sandbox mode.
- **Runtime settings** (`settings.py`): on/off and model per runtime, saved in the board directory (environment variables
  still work). **Getting results out:** download, zip, open folder, and a one-folder export that never overwrites.
- **Board persistence:** the board keeps its cards and events in one sqlite connection shared by request threads and task
  workers. Every use of it takes `Board._lock` (an `RLock`); `tests/test_board_threads.py` fails without it.
- **Local-only guard** (`guard.py`): the board refuses a foreign `Host` header (DNS rebinding) and changing requests from
  another origin.

### 4.7 Connections (`zyven/connections/`)
A *connection* is an MCP server: a hosted URL or a local command (the latter refused unless `ZYVEN_ALLOW_STDIO_CONNECTORS=1`).
Keys and OAuth tokens live in a separate local file that the API never returns, and a server error that echoes a secret is
masked. OAuth uses the MCP SDK (PKCE, dynamic client registration, refresh) with Zyven's storage, a callback that checks
the OAuth `state`, and the `iss` check that services such as Notion require. The SDK treats a stored token as never expiring
in a new process, so the expiry is saved and restored (otherwise an old token is sent and rejected instead of refreshed).
An expired or revoked sign-in is reported plainly and the dead token is forgotten, so the card returns to "Not signed in".
After a Test, each tool is marked read-only or *asks first* from the server's own hint; an unknown hint means ask.

### 4.8 The Zyven Hub (`zyven/hub/`)
The board serves an MCP endpoint at `/hub/mcp` so a coding agent that brings its own model can use Zyven's tools. A task
that asks for them gets a per-run bearer token (revoked when the run ends). For each run the hub starts, in parallel and
each in a task of its own, a ToolBox per enabled connection (with prefixes) and per verified skill. A tool a server does
not mark read-only calls the Control center's approval flow before it runs; the agent's call blocks until the user decides,
and a denial returns "Denied ... do not retry". A `zyven_status` tool lets the agent ask why a service is missing.
Codex is configured by `-c` flags (approve mode so it does not ask a second time, a long tool timeout, the token in the
environment); OpenCode by its project config; Claude Code by a config file in the task folder.

### 4.9 Coding agents as compile roles (`zyven/ai/agent_provider.py`)
Any of the four compile roles (architect, compiler, tester, repair) can be served by a coding agent instead of the chat
model: `zyven compile ... --agent codex`, or one role at a time (`--compiler claude:opus --tester qoder`).
`AgentProvider` is a `ModelProvider` whose `chat()` is one headless run of the CLI. It reuses the Control center
adapter's command line and output parser, narrowed to "answer in text, change nothing":
- a fresh, empty temporary folder, deleted afterwards
- Codex in its `read-only` sandbox; Claude Code with `--tools ""`; OpenCode with every permission denied; Qoder with
  `Read` only

The conversation is flattened into one prompt, with the JSON Schema appended for structured calls. The last agent message
is the reply, and the JSON object is cut out of any prose around it. The reply is trusted exactly as much as a chat
model's, which is not at all: the same schema validation, reference resolution, policy check and six gates apply.
`compile_capability(..., roles={...})` routes each role. `provenance.json` records each role's provider under
`"roles"`, and `scripts/check_open_models.py` scans those entries, so a committed result cannot hide a closed model in a
single role. Agents refuse `chat(tools=...)`, because they bring their own tools and cannot drive Zyven's agent loop.

### 4.10 `zyven verify`: checks for any MCP server (`zyven/mcpverify/`)
The compile gates need the library and a spec. A third-party server has neither, so `verify` checks it from the outside,
from what the server itself says and does. `probe.py` connects to it (a stdio command, a streamable HTTP URL, or a
command run in the sandbox with `--docker IMAGE --mount HOST:/PATH`) and records:
- the handshake and the tool list
- a second listing on a fresh connection
- with `--probe`, calls with input that the tool's own schema forbids: missing required parameters, or a wrong type

`checks.py` is pure and turns that record into seven checks:

| Check | Fails when |
|---|---|
| handshake | the server does not start, finish the handshake or list its tools in time |
| schemas | a tool name is invalid or repeated, or a schema is not valid JSON Schema (Draft 2020-12) |
| descriptions | names, descriptions, parameters or server instructions carry tool poisoning (see the list below) |
| annotations | a tool is marked both read-only and destructive (a missing hint is a warning) |
| stability | definitions differ between two connections or from a lock file (a rug pull) |
| robustness | (`--probe`) input the schema forbids is accepted, or the server stops answering |
| isolation | a warning, not a failure, when the server ran on the host, or in the sandbox with `--allow-network` |

The poisoning patterns: invisible Unicode tag characters (decoded back to readable text in the report), bidi overrides,
terminal escape sequences (a CLI client prints them straight to the screen: SGR 8 concealed text is read back, cursor
movement and erasing, OSC 8 hyperlinks with their real targets, OSC 52 clipboard writes, 8-bit forms included), other
control characters such as backspace, `<IMPORTANT>` blocks, "do not tell the user", requests to read credential files, and URLs to send data to. The instruction patterns are matched on the raw text and
again with every escape sequence and invisible character removed, so splitting a phrase with them does not hide it.

A stdio server gets the SDK's minimal environment, never the caller's secrets; `--env NAME` passes a variable through.
Sandbox containers are named, force-removed after each connection (some Node servers outlive their input), and all get the
host name `zyven-sandbox`, so a server cannot tell runs apart by it. desktop-commander writes the host name into a tool
description, which first looked like a rug pull.

### 4.11 `zyven mcp`: verified skills over stdio (`zyven/hub/stdio.py`)
The same tools as the board's hub, as a plain stdio MCP server that a coding agent starts itself, with no board running:
`claude mcp add zyven -- ... zyven mcp`, or `codex mcp add ...`; `zyven mcp --print-config` prints both. It reuses
`HubSession`: every verified skill in the library runs in its sandbox, plus `zyven_status`. The tools are annotated
read-only, which is true by construction (policy plus sandbox). Connected services are added only with `--connections`.
Without the board there are no approval cards, so the agent's own permission prompt is the gate.

### 4.12 Install layout, setup and reassembly (`zyven/paths.py`, `zyven/setup.py`, `zyven/compiler/reassemble.py`)
A git checkout keeps `workspace/`, `.env`, `skills/` and `catalog/`. An installed copy (pipx, uvx, pip) keeps everything
under `~/.zyven`, or `ZYVEN_HOME`. The wheel ships the sandbox files, the catalog and, when built, the dashboard
(`hatch_build.py`).
- **`zyven setup`** builds the sandbox image, labelled with a hash of the files it bakes in.
- **`zyven doctor`** reports when the image is stale, because gates on an old image give wrong results.
- **The board starts without a model key.** `NoModel` makes only the chat-model features explain what is missing.
- **`zyven reassemble`** rebuilds old skills with the current harness, with no model calls. It reuses the saved spec,
  bodies and differential cases, reruns all six gates, and puts the old `server.py` back on any failure or crash.

### 4.13 Export, client configs, upstream drift (`zyven/export.py`, `zyven/mcpverify/configs.py`, `zyven/outdated.py`)
- **`zyven export`** writes a verified skill as a standalone MCP server:
  - `server.py`, unchanged
  - a `pyproject.toml` and a `Dockerfile` that install the library at the exact verified commit. A pip
    `#subdirectory` is worked out from the checkout when the package is not at the repository root.
  - the evidence files, copied, plus a README with the gate results and client config

  Only skills whose `validation-report.json` passed can be exported.
- **`zyven verify --config` / `--discover`** reads the MCP server lists of common clients (JSON `mcpServers` / `servers`
  blocks, including per-project blocks in `~/.claude.json`, and Codex's `config.toml`) and runs the outside-in checks on
  each server. `env` values reach their server only. URL labels drop the query string and user info.
- **`zyven outdated`** compares each skill's verified commit with upstream HEAD (`git ls-remote`). With `--fetch` it also
  counts the commits behind and lists the changed files inside the modules the skill uses, mapped from the spec's
  `included_symbols`.

### 4.14 Measuring the gates (`eval/mutation_test.py`)
The mutation harness injects small bugs into a verified skill's tool bodies and reruns the gates with the skill's own
differential cases (section 6 of the README has the numbers). Two guards keep it honest:
- **Controls.** The unmutated skill must pass the same path before and after the mutants.
- **Docker failures.** A failure caused by Docker itself stops the run. It is never counted as a catch.

`--calibrate` drops, and lists, Tester cases that fail on the unmutated skill: the standard rule that a test must pass
on the original program.

The Tester's coverage is checked deterministically (`coverage_gaps`):
- tools with no case
- optional parameters never set, and never left out
- return fields never checked

Coverage is judged only on cases that pass the sandbox's own reference checks (`reference_problem`). Tools with gaps
are asked about once more, with the rejection reasons quoted.

## 5. Trust Boundaries & Threat Model

| Boundary | Inbound / Outbound | Security Mechanism |
|---|---|---|
| **External Repository Source** | Inbound from GitHub | Cloned only at fixed immutable commits (`catalog/repos.json`). AST analyzed offline; never executed on the host. |
| **Model Generation** | Inbound from LLM | Parsed with strict Pydantic schemas. Symbols verified by `RefResolver`. Code checked by AST policy before sandbox execution. |
| **Sandbox Execution** | Adapter & Tests → Container | Docker container with `--network none`, read-only roots, non-root user, CPU/memory limits, dropped capabilities. |
| **Skill Runtime** | Agent → Skill Server | Verified skills run in the same container when the agent calls them; a sandbox test checks that a skill has no network and can write only to `/tmp` at runtime. |
| **Human Approval** | Agent → Human Reviewer | The agent cannot compile or load outside code without explicit user approval via UI/API (`/api/cards/{id}/decision`). |
| **Connected Services** | Agent → Third-party MCP server | Enabled by the user after a Test shows the tool list. Tools not marked read-only wait for an approval card. The read-only hint comes from the server itself and is not verified by Zyven. Tool output is untrusted text. |
| **Coding Agents** | Control center → Codex / OpenCode / Qoder CLI / Claude Code / Antigravity | Optional, off by default, each in its own containment (see 4.6). Task text goes to the provider each program is signed in to. |
| **Zyven Hub** | Coding agent → `/hub/mcp` | Per-run bearer token, revoked at run end; only that run's connections and skills; approvals for non-read-only tools. |
| **`zyven mcp` (stdio)** | Coding agent → verified skills | The agent starts the process; skills run sandboxed and are read-only by construction. Connected services only with `--connections`, then gated by the agent's own permission prompt. |
| **Coding agent as compile role** | Pipeline → agent CLI → pipeline | Empty temp folder, minimal tools; the reply is parsed and gated like any model output. Code and prompts go to the agent's provider. |
| **`zyven verify` target** | Unknown MCP server → Zyven | No tool calls without `--probe` (probes send only schema-invalid input); minimal environment; `--docker` for untrusted code; containers removed afterwards. |
| **Full PC Access** | User → Agent without a sandbox | Two deliberate steps (environment switch, per-task confirmation); never for repeating tasks; not through the web page alone. |
| **Local Board API** | Browser / other sites → Board | No login: only this machine's `Host`, and changing requests from other origins are refused. |
| **Model Verification Overclaim** | Failed Compile → Agent | If verification fails, the agent is explicitly instructed that the capability is unverified, tools are withheld, and cards enter `UNVERIFIED` state. |

## 6. Evaluation Harness (`eval/`)

`eval/run_eval.py` runs a task suite twice with the same model and budget: the model alone, then with a compiled skill attached
(`--skill skills/<name>/server.py`). Suites: `nepali`, `stdnum`, `global`, `packaging`, `networkx`. Ground truth is computed by
the source library itself; questions are generated from a seed, and the model's reply must end with an `ANSWER:` line.
`--max-tokens` sets the per-call output budget (4096 by default; a reply that hits the cap counts as wrong), and
`--baseline-only` runs only the model alone. Results go to `eval/results/run-<time>.{jsonl,md}`. See `README.md` for the
numbers and `LIMITATIONS.md` section 5 for what they do and do not show.
